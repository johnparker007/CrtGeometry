# CRT Geometry - Implementation Plan

## Purpose

CRT Geometry is a Windows desktop application for managing game- and system-specific CRT geometry profiles, with MAME integration and generation of compact data for an Arduino Nano that writes geometry settings to a television's M24C16 NVRAM.

The application is the source of truth for profiles, game mappings, imported MAME metadata, and generated firmware data. The Arduino firmware remains deliberately small and deterministic.

## Core principles

- Build and validate in small phases.
- Each phase should be implemented on a branch/PR, tested manually, reviewed, then merged before the next phase.
- SQLite is the authoritative application data store.
- CSV is a round-trip interchange format, not the primary database.
- MAME XML is imported, normalized, and stored; the original XML is not committed to the repository.
- MAME ROM shortname is the stable machine identifier. Full title/description is the primary user-facing search field.
- Geometry profile data is five values: HSH, VSL, VAM, VSC, VSH.
- Do not assume forever that width + height + orientation + refresh is sufficient to identify equivalent CRT timing. Preserve additional timing fields from MAME when available so the matching strategy can be refined without redesigning the database.
- Firmware-generated data must be deterministic: identical database state produces byte-for-byte identical generated output.

## Recommended technology

- C# / .NET 10
- WPF
- SQLite
- Microsoft.Data.Sqlite
- MVVM-style separation between UI, services, persistence, and domain models. Avoid adopting a large UI framework unless it has a demonstrated need.
- Unit tests for parsing, matching, profile propagation, CSV round-trip, and firmware-data generation.

# Domain model

## Game

Imported from MAME.

Minimum fields:

- `RomName` - stable MAME shortname / machine name, unique
- `Description` - full MAME title shown to users
- `Year`
- `Manufacturer`
- `CloneOf` when present
- runnable/device/BIOS/mechanical flags where present
- coin input count where present
- display metadata
- assigned `ProfileId`, nullable
- source MAME import/version metadata

The UI should let the user search by description, ROM shortname, manufacturer, and year. Users should normally select a game by its full human-readable description and should not need to know the ROM shortname.

## Display / Video signature

Preserve MAME display fields available in the imported XML, including at least:

- width
- height
- rotation/orientation
- refresh rate
- display type where available
- timing/blanking/raw fields where available in the source MAME XML

The first matching strategy may use a normalized signature based on resolution + orientation + refresh, but the raw imported timing metadata must remain available.

Refresh comparisons must not depend on fragile formatted strings. Store a numeric representation with an explicit comparison tolerance or normalized representation.

## GeometryProfile

Fields:

- `Id` - stable profile ID, intended to fit in one byte; reserve 0 as undefined if convenient
- HSH 0..63
- VSL 0..63
- VAM 0..63
- VSC 0..63
- VSH 0..63
- Notes, optional
- calibration source game, optional
- created/updated metadata if useful

Multiple games may reference the same geometry profile.

A profile may initially be calibrated from one game. The application should retain that source/provenance even when the same profile is automatically assigned to many matching games.

## Non-MAME systems

The application must also support manually created entries for consoles/computers/other video sources. These do not require a MAME ROM name. They can reference the same GeometryProfile model and may later gain system-specific metadata.

The initial MAME implementation should not make the database schema impossible to extend to these sources.

# MAME import

The known source is an older MAME installation, probably around MAME 0.139. A generated `mame.xml` is approximately 42 MB.

Importer requirements:

- Stream the XML. Do not load the full document into memory.
- Tolerate the older MAME XML schema rather than assuming current MAME-only fields.
- Read machine/game name, description, year, manufacturer, flags, input information, display information, clone information, and any useful raw timing metadata that exists.
- Import should be repeatable. Reimporting a newer or regenerated XML should update MAME metadata without deleting user-created calibration/profile information.
- Record enough import metadata to identify the imported MAME version if the XML exposes it.

Initial arcade-video filtering should use available source fields rather than a manually maintained game whitelist. Candidate rules:

- exclude BIOS entries
- exclude devices
- exclude non-runnable entries
- exclude mechanical entries
- require at least one video display
- normally require a raster display for this CRT use case
- use coin inputs as a strong arcade-machine signal where the old XML exposes them

The filtering logic should be visible/testable rather than buried inside the XML reader. Store/import enough raw classification information that filtering can be changed later without reparsing XML where practical.

Video gambling/slot-style machines may still pass a coin+raster filter. The application should support additional exclusion rules/categories later if needed.

# Calibration workflow

Primary workflow for adding a new measured profile:

1. User opens calibration/profile editor.
2. User searches the imported MAME catalogue using a human-readable title such as `Donkey Kong`.
3. Search results show full title plus useful disambiguation such as year/manufacturer and optionally ROM shortname.
4. User selects the exact MAME entry.
5. App internally uses its ROM shortname and imported video metadata.
6. User enters measured HSH/VSL/VAM/VSC/VSH values.
7. App determines whether that video signature already has a profile or whether a new profile should be created.
8. User can inspect which other games will match/inherit the profile before accepting propagation.
9. App stores the selected game as calibration provenance and assigns the profile to matching games according to the current matching rules.

The app must make it easy to override automatic assignments when real hardware testing proves two apparently matching modes need different profiles.

# Profile matching

Initial hypothesis from hardware testing:

Games with the same active resolution, orientation, and refresh often share CRT geometry settings. Example observed case: games with 288 x 224 vertical output at 60.606061 Hz can share geometry despite being from very different Namco hardware eras.

This is a hypothesis, not a permanent invariant.

Implementation requirements:

- encapsulate video signature generation/matching in one service
- do not duplicate the matching formula throughout UI/database code
- make it possible to refine the signature later using preserved timing data
- provide a view of all games matching a selected signature/profile
- provide manual assignment/override support

# CSV import/export

CSV exists for round-trip editing/backup, not as the application's primary database.

Requirements:

- export app-owned editable data in a documented format
- import that same format back
- validate ranges, required IDs, duplicate IDs, missing references, and malformed values before applying changes
- support a clear replace/merge policy rather than silently overwriting ambiguous data
- no special migration support is required for the old Google Sheet; the existing handful of rows can be entered manually

# Firmware generation

The desktop application should generate a dedicated firmware include rather than editing arbitrary sections of the `.ino` sketch.

Target:

```text
firmware/CrtGeometryController/GeneratedDatabase.h
```

The handwritten firmware includes it:

```cpp
#include "GeneratedDatabase.h"
```

Generated content should eventually include:

- geometry profile table
- game -> profile mappings
- packed game-name data
- offsets/index data needed for alphabetical browsing
- compile-time counts/constants

Generated file must contain a prominent comment stating it is generated and should not be manually edited.

Generation should be deterministic and covered by tests.

## Geometry profile storage

Up to 256 profile IDs is the current intended design, allowing a one-byte profile ID.

Each geometry profile needs five bytes:

```text
HSH VSL VAM VSC VSH
```

256 profiles therefore require only 1,280 bytes if represented as a direct fixed table in PROGMEM. Direct indexing is acceptable and attractive because profile ID can equal table index.

Profile 0 may be reserved as undefined/invalid.

## Game-name storage

The Nano needs enough game-name data to select a game without a printed lookup list.

Names can be shortened specifically for the 20-character LCD while the desktop application retains the full MAME title.

Candidate compact encoding:

- uppercase display names
- 6-bit character alphabet
- required alphabet: A-Z, 0-9, space
- use remaining codes for useful punctuation such as `-`, `/`, `.`, `'`, `&`, `+`
- pack names into a continuous bitstream
- no per-name NUL terminator
- derive a name's bit length from the current entry offset and the next entry offset
- store one-byte profile IDs
- alphabetically sort game lookup entries at generation time

Do not finalize the binary/generated format until the Nano browser UI is implemented and measured for flash usage.

# Arduino / Nano behavior

The existing hardware prototype uses:

- Arduino Nano / ATmega328P
- 20x4 HD44780-compatible LCD in 4-bit parallel mode
- 2 clickable rotary encoders
- M24C16W TV NVRAM through a manual DPDT switch that transfers SDA/SCL between TV and Nano
- common logic ground between TV and Nano

The firmware currently writes these TV settings:

```text
HSH 0x0103
VSL 0x0109
VAM 0x010A
VSC 0x010B
VSH 0x010C
check byte 0x01AD
```

Known encodings from NVRAM dumps:

```text
HSH raw = service-menu HSH - 38, modulo 256
VSL raw = UI value
VAM raw = UI value - 4
VSC raw = UI value
VSH raw = UI value + 2
```

The TV firmware has an empirically observed HSH reload error of approximately +7 in the useful range. The Nano currently compensates when writing desired effective HSH. Keep the compensation separate from the actual NVRAM encoding so it can be changed after additional testing.

The check byte at 0x01AD behaves additively for the characterized geometry changes. Existing firmware preserves its unknown contributions and adjusts it by the raw-byte deltas of the five known geometry bytes.

Writes must be read-modify-write, touch only characterized addresses, and verify by reading the written bytes back.

## Existing pin allocation

```text
LCD
D12 = RS
D11 = E
D5  = D4
D4  = D5
D3  = D6
D2  = D7

I2C
A4 = SDA
A5 = SCL

Encoder 1
A3 = CLK
D10 = DT
D9 = SW

Encoder 2
D8 = CLK
D7 = DT
D6 = SW

Currently free (not assigned to future features)
A0, A1, A2, D13
```

D13 was deliberately avoided for rotary CLK because the onboard LED circuitry caused poor behavior.
Encoder 3 has been removed; A0/A1/A2 remain unassigned pending finalized electronic
bus-switch, IR, and transistor/MOSFET backlight circuits.

The encoders require proper quadrature decoding rather than simple CLK-edge sampling. The working implementation uses a state transition table and accumulation to one movement per detent.

# Intended Nano UI evolution

The current manufacturer/platform menu is expected to be replaced by a game/profile-oriented UI once generated database support exists.

Two operations must remain available:

## Normal play

- browse/select a game from compact on-Nano game data
- selected game resolves to a profile ID
- LCD displays profile/geometry information
- click writes current geometry to NVRAM and verifies

The final browsing interaction should be optimized after testing with hundreds of names. Alphabetical grouping/jumping is preferable to forcing hundreds of single-step rotations.

## Calibration/manual mode

Manual calibration is essential and must not be removed.

The user sometimes spends significant time adjusting the five values for previously unsupported video modes. A long-hold or similarly deliberate action should enter manual geometry editing. Manual mode must allow selecting and adjusting all five geometry values and repeatedly writing them during calibration.

Leaving/reselecting a baked profile should restore its generated values; temporary manual edits should not mutate generated firmware profile data.

# Desktop UI areas

The exact visual design can evolve, but the finished application should provide these functional areas:

## Games

- searchable/filterable grid
- full MAME title first
- ROM shortname visible as secondary information
- year/manufacturer
- video mode/signature
- assigned profile
- filters for assigned/unassigned and inclusion/exclusion status

## Profiles / Calibrations

- editable profile grid
- ID and five values
- notes/source game
- matched game count
- create/edit/delete with validation
- inspect all games mapped to a profile

## MAME import

- choose XML file
- show import progress
- show source/version metadata when available
- summarize imported/excluded machine counts
- reimport without destroying user profile/calibration data

## Firmware export

- generate `GeneratedDatabase.h`
- report profile/game counts and estimated generated storage size
- validate that profile count/ranges and packed offsets fit the Nano format

Later enhancement:

- optionally invoke `arduino-cli` to compile and upload firmware to a selected Nano after generation
- keep this separate from initial deterministic source generation

# Non-MAME systems

After MAME functionality is established, add manually defined sources for consoles/computers connected to the same CRT/SCART switching setup.

These entries need:

- display/system name
- geometry profile
- optional notes about console/computer/video mode

They should eventually be selectable on the Nano alongside MAME games without pretending they have MAME metadata.

# PR/review workflow

For each phase:

1. Codex implements only the agreed phase on a branch.
2. Codex opens a PR with scope, design notes, tests, and manual test instructions.
3. User runs the application/hardware and reports results.
4. Review checks correctness, architecture, forward compatibility, generated-data stability, and edge cases.
5. Fixes are made on the same PR.
6. Merge only after manual acceptance and review.
7. Update this plan when hardware/data discoveries change assumptions.

Avoid giant multi-phase PRs.

# Items intentionally not finalized yet

The following should be decided using real imported data/hardware testing rather than prematurely fixed in architecture:

- exact definition of the video-mode/signature key
- exact arcade-only filtering beyond the initial MAME metadata rules
- exact Nano alphabetical game-navigation interaction
- maximum shortened game-name length
- final 6-bit punctuation alphabet
- exact packed-game index layout
- whether direct numeric profile selection remains exposed in the final Nano UI
- whether the HSH +7 compensation remains constant across every useful calibrated range
- whether Arduino CLI upload should be bundled/configured or remain an external dependency
